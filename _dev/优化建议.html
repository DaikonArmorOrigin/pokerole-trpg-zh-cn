01

没有 index.html，这个站现在发布不出去

致命
现象
目录里只有 index-v2.html。GitHub Pages、Vercel、Netlify 都只认 index.html 作为入口，打开会是 404 或目录列表。
改法

把 index-v2.html 改名为 index.html（旧的留一份 index-v2.html.bak 以防万一）。

如果打算用 GitHub Pages，还要再建一个空的 .nojekyll 文件——否则 Jekyll 会把下划线开头的 _sidebar.md 当特殊文件忽略掉，侧栏直接消失。这是 docsify + GitHub Pages 最经典的一个坑。

# 在项目根目录执行
mv index-v2.html index.html
touch .nojekyll
02

目录有 69 个链接，只有 5 个能打开

致命
现象
侧栏列了 13 章 + 附录，但对应的 13 个 md 文件（04-pokemon-battles.md、05-catching.md … appendix-glossary.md）一个都还没写。读者点进去就是「页面走丢了」，而面包屑还理直气壮地显示着章节名。

03

7 张图 8.3 MB，手机打开要等很久

致命
现象
image.png ~ image-6.png 一共 8.3 MB。但它们的实际尺寸只有 600×800 左右—— 617×792 的图却占了 1.87 MB，说明是没压缩过的 PNG 截图。 同时它们躺在项目根目录，和你在《写作手册》里定的「图片统一放 assets/img/」规则自相矛盾； alt 文本也全是占位的 alt text。
影响
转到 WebP（质量 82）后，这 7 张大概能压到 400 KB 左右，体积降到原来的 5%，肉眼几乎看不出差别。
改法

① 移到 assets/img/ 并改成有意义的文件名（sheet-trainer.png、sheet-pokemon.png…）；
② 批量转 WebP；
③ 顺手把 alt 补成真正的描述——这既是无障碍，也是 SEO。

# 装个 Pillow 后批量处理
python -m pip install pillow
python tools/optimize_images.py

这一步我可以直接帮你跑完，包括改 md 里的引用路径。

04

首页的「下一节」按钮永远点不动

体验
现象
读者从首页进来，底部的「上一节 / 下一节」两个按钮都是禁用状态（已实测确认）。因为 _sidebar.md 里没有指向 README 的条目，findCurrentIndex() 返回 -1，于是前后都判定为「没有」。
影响
新读者读完欢迎页，唯一的出路是去左上角点开侧栏——白白丢掉一次「开始阅读」的引导。
改法

assets/app.js 第 381 行附近：

var isHome = /^readme(\.md)?$/i.test(currentPath);
var prev = idx > 0 ? links[idx - 1] : null;
var next = idx >= 0
    ? (idx < links.length - 1 ? links[idx + 1] : null)
    : (isHome ? links[0] : null);   // 首页 → 指向第一节
05

侧栏当前项右边多出一条绿线

视觉
现象
vendor/vue.css 第 622 行给激活项留了 border-right: 2px solid（绿色）。你的主题覆盖了背景色、文字色和 border-left-color，唯独没管右边框，于是红底上挂了一条绿线。
改法

在 assets/theme.css 第 1421 行那段「侧边栏当前页高亮」里补一行：

.sidebar ul li.active > a,
.sidebar-nav li.active > a {
    border-right: none;
}

06

侧栏把「页」和「页内锚点」混在一起了

结构
现象
「宝可梦对战」一章在侧栏被拆成 10 条锚点链接，同时 subMaxLevel: 3 还会把页面里的 H2/H3 自动再列一遍。等这一章真写出来，侧栏会膨胀到二十几条同页链接。
影响
更麻烦的是 findCurrentIndex() 为了绕开重复锚点，取的是「第一个匹配」——一旦 04 章落地，「上一节 / 下一节」会永远卡在该章第一条，翻不到下一页。
改法

侧栏只放页面级链接（一章一条），页内导航交给右侧浮动的 TOC，或者干脆把 subMaxLevel 降到 0。 顺带一提：中文锚点（#属性、#先攻）在不同浏览器里编码方式不一致，跨平台容易点不动，这也是少用锚点的一个理由。

07

用 setTimeout 轮询等侧栏渲染

健壮性
现象
refreshChrome() 里每 120ms 检查一次侧栏有没有出来，最多重试 5 次。网络慢的时候 600ms 不够，面包屑就停在「加载中…」；网络快的时候又白等。
改法

docsify 提供了 hook.ready，而侧栏是异步 fetch 的，更稳的做法是观察节点出现：

var nav = document.querySelector('.sidebar-nav');
if (nav) { refreshChrome(); }
else {
  new MutationObserver(function (m, obs) {
    if (document.querySelector('.sidebar-nav')) { obs.disconnect(); refreshChrome(); }
  }).observe(document.body, { childList: true, subtree: true });
}
08

面包屑靠「猜 DOM 结构」拿分组名

健壮性
现象
getGroupLabel() 沿着 li → ul → li 一层层往上爬，再从子节点里捞第一个非空文本当作分组名。只要 _sidebar.md 换个写法（比如去掉加粗、改成 H3 标题、或多套一层列表），面包屑就会显示成空白或错误的分组。
改法

把「分组 → 页面」的对应关系从 DOM 里解放出来，单独维护一份结构，例如在 assets/ 下加一个 nav-data.js，与 _sidebar.md 同源生成。虽然多一个文件，但改目录时不会连累面包屑和翻页逻辑。

09

theme.css 1777 行、43 个 !important

可维护性
现象
从 index.html 的内联样式抽出来时保留了 8 空格缩进；颜色大量硬编码（#4b5563、#ea580c…），而 :root 里只定义了 7 个变量；!important 用了 43 次，多数是为了压过 vue.css。
影响
现在还能改得动，但每加一个样式都要试一下会不会把别处顶掉。文件到 3000 行时会变成泥潭。
改法

不用大动。分三步：① 用编辑器格式化统一缩进；② 把重复出现的颜色收进 :root；③ 在文件顶部加一个目录注释（/* 1. 变量 2. 布局 3. 侧栏 … */）。半小时的事，后面省很多。

10

有一批写了但没用的样式和代码

清理
现象
theme.css 里那套 img.sheet-figure（角色卡示意图，1486 行起）在 md 里一次都没被调用； app.js 里的 window.toggleInsert 兼容层、.app-nav 的隐藏规则，也都已经没有对应内容了。
改法

两种处理：要么在 md 里真正用起来（![训练家卡](assets/img/sheet-trainer.webp){.sheet-figure}，配合 docsify 的 image 属性支持），要么删掉。留着不用比删掉更让人困惑。

11

正文没有中文字体栈

观感
现象
正文继承的是 "Source Sans Pro", "Helvetica Neue", Arial——这三个字体都没有汉字。中文实际是靠浏览器逐个字回退到系统字体，Windows 是微软雅黑、macOS 是苹方、安卓是思源，三端字形和行高都不一样。
改法
.markdown-section {
    font-family: -apple-system, "Segoe UI", "PingFang SC",
                 "Hiragino Sans GB", "Microsoft YaHei",
                 "Source Han Sans SC", sans-serif;
}

顺带：中文正文的 line-height 建议 1.85～1.9，比英文需要的更松；你现在的 1.8 已经接近了。

关于方向你说还没想好——这里有个判断依据

规则书网站有两类读者、两种用法，而它们要的东西几乎相反：

场景什么时候发生最需要什么
读第一次接触，从头看排版、插图、章节引导、叙事感
查跑团进行中，随时跳搜索、速查表、锚点、离线、手机可读

你现在 90% 的设计精力花在「读」上，这没错——它决定了别人愿不愿意留下来。 但一个规则书被打开的次数，绝大部分来自「查」。这部分现在几乎是空的。 所以下一步的投入产出比，明显在「查」这一侧。

推荐

继续用 docsify，把力气花在「查」上

加一页 /quickref 速查（相克表 + 异常状态 + 价格 + 伤害表挤在一屏，可打印成 GM 屏），再做 Ctrl+K 搜索和 PWA 离线。改动小、见效快，不打断你写内容的节奏。

迁移到 VitePress / Astro

SEO 和首屏性能会好一个量级（内容会被预渲染成静态 HTML）。代价是要装 Node 工具链、学构建命令，写作流程从「存 md 就生效」变成「写完要 build」。对你现在的情况，不划算。

保持现状，专心翻译

也完全合理。那就只修 P0 的五条，其余一律不管——把有限的时间放在内容上，本来就是这个项目最稀缺的资源。

一句题外话：你已经有《写作手册》和《关键词对比.txt》了，这说明你在认真对待「术语一致性」。 这件事其实可以自动化——写个小脚本扫描所有 md，对照术语表找出「同一个英文词被译成两种中文」的地方，每次提交前跑一遍。 对翻译项目来说，这比任何视觉优化都值钱。
